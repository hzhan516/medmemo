# Design Note v1.0: Configuration-Driven Model Access Architecture

> 🌐 [中文版本](../i18n/zh-Hans-CN/design/v1.0-config-driven-design.md)

- **Status**: Accepted
- **Date**: 2026-05
- **Deciders**: Tech Lead
- **Scope**: v1.0 — Multi-Model Free Configuration System

## Context

MedMemo v1.0 aims to support arbitrary OpenAI-compatible LLM providers without hardcoding vendor-specific adapters in the backend. The desktop application must allow users to dynamically add, edit, and switch between providers (OpenAI, Kimi, DeepSeek, Claude, Ollama, etc.) through a unified UI.

Before v1.0, the codebase contained vendor-specific adapters (`OpenAIAdapter`, `LocalAdapter`) with hardcoded endpoints, authentication logic, and request formats. Adding a new provider required backend code changes, recompilation, and release — unacceptable for a desktop tool targeting rapid provider ecosystem evolution.

## Decision

Adopt a **configuration-driven architecture** where the backend uses `OpenAIAdapter` for OpenAI-compatible cloud endpoints and `LocalAdapter` for Ollama/llama.cpp endpoints. Provider differences are resolved through user-editable runtime configuration.

### Core Principle

```
Backend: Zero vendor-specific code
Frontend: Zero vendor-specific logic (except static template JSON)
User: Full control over API Host, Key, Model ID, Temperature, Timeout
```

### Key Design Points

1. **Adapter factory**: `internal/adapters/ai/provider.go` maps `ProviderConfig` to `OpenAIAdapter` for OpenAI-compatible endpoints or `LocalAdapter` for local Ollama/llama.cpp endpoints.

2. **Unified ProviderConfig**: A single `pkg/models.ProviderConfig` struct serves HTTP client calls, SQLite persistence, Wails serialization, and frontend state management. Eliminates DTO proliferation.

3. **Static Template JSON**: 21 pre-built provider templates (OpenAI, Kimi, DeepSeek, Claude, Ollama, etc.) stored as a frontend static JSON file. Adding a new template requires **only a JSON edit** — no backend release.

4. **Runtime Model Switching**: The chat interface's `ModelSwitcher` reads the active `ProviderConfig` and passes `modelId` to `SendMessageStream`. New messages use the newly selected model; historical messages are preserved.

5. **Health Detection Decoupled**: `HealthEngine` independently polls each provider's `/v1/models` endpoint. It does not depend on adapter internals, using standard library `net/http` directly.

## Consequences

### Positive Impacts

- **Zero backend code for new providers**: Adding support for a new OpenAI-compatible service requires only a frontend JSON template entry.
- **Uniform error handling**: All providers share the same `LLMError` classification (4xx = non-retryable, 5xx/429/timeout = retryable).
- **Testability**: The generic client can be fully tested against a single `httptest` server; no need to mock 20+ vendor APIs.
- **User empowerment**: Power users can add private deployments, custom endpoints, or experimental models without waiting for app updates.

### Negative Impacts

- **Non-OpenAI-compatible providers unsupported**: Vendors with proprietary APIs (e.g., some older Chinese LLM platforms) cannot be used without a translation proxy. Mitigation: Ollama's OpenAI-compatible mode covers most local models; cloud providers are rapidly adopting the OpenAI API format.
- **Feature parity loss**: Provider-specific features (e.g., OpenAI's function calling, Kimi's context caching) are not exposed. Mitigation: v1.0 focuses on basic chat completion; advanced features can be added via optional `ProviderConfig` extension fields in future versions.
- **Template maintenance burden**: 21 templates require periodic updates (model lists, default models). Mitigation: templates are frontend-only JSON; CI validates schema integrity.

## Alternatives Considered

| Alternative | Rejection Reason |
|:------------|:-----------------|
| **Vendor-specific adapter per provider** (`OpenAIAdapter`, `KimiAdapter`, `DeepSeekAdapter`, ...) | High maintenance cost; every new provider requires backend code, tests, and release cycle |
| **Plugin architecture (dynamic .so / wasm loading)** | Over-engineering for v1.0; adds significant complexity (plugin lifecycle, ABI stability, security sandbox) for marginal gain |
| **Proxy server approach (central MedMemo API gateway)** | Violates local-first pillar; introduces network dependency and privacy risk |
