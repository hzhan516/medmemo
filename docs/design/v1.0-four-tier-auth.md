# ADR-002: Four-Tier Progressive Authentication System

> 🌐 [中文版本](../i18n/zh-Hans-CN/design/v1.0-four-tier-auth.md)

- **Status**: Accepted
- **Date**: 2026-05
- **Deciders**: Tech Lead
- **Scope**: v1.0 — Multi-Model Free Configuration System

## Context

MedMemo targets a diverse user base including privacy-conscious technical users, family health managers, and office workers. A significant barrier to adoption is the API Key acquisition process: many potential users have subscriptions to LLM services (ChatGPT Plus, Kimi Premium) but do not possess or know how to obtain API Keys.

The v1.0 onboarding flow must minimize friction while maintaining security and local-first principles. We need a progressive authentication system that:
1. Automatically detects existing credentials (CLI tool caches)
2. Falls back to OAuth browser authorization for users without API Keys
3. Supports traditional API Key input as a last resort
4. Provides a fully offline local model option as ultimate fallback

## Decision

Implement a **four-tier progressive authentication system** ordered by user convenience (least effort first):

```
Tier 1 ── CLI Token ──────────────┐
        (zero-config, auto-detect) │
Tier 2 ── OAuth Device Flow ──────┤──→ ProviderConfig.AuthMethod
        (browser auth, no key copy)│    (cli_token / oauth_device /
Tier 3 ── API Key ────────────────┤     api_key / service_account)
        (manual input, guided)     │
Tier 4 ── Local Model (Ollama) ───┘
        (fully offline, one-click)
```

### Tier 1: CLI Token Authentication

**Mechanism**: Detect and read cached access tokens from locally installed CLI tools.

- **Kimi CLI**: Parse `~/.kimi/credentials/kimi-code.json` → extract `access_token`
- **Gemini CLI**: Parse `~/.config/gcloud/application_default_credentials.json` → extract `refresh_token` (auto-refresh via Tier 2 mechanism)

**User experience**: Open MedMemo → "We detected your Kimi CLI login. Use it?" → One click → Done.

**Implementation**: `CLITokenService` (`internal/adapters/auth/cli_token_service.go`)

### Tier 2: OAuth 2.0 Device Authorization Grant (RFC 8628)

**Mechanism**: Backend requests device code → frontend displays user code + verification URL → user authorizes in browser → backend polls token endpoint → receives access_token.

**User experience**: Open MedMemo → "Sign in with Kimi" → See 8-digit code + QR code → Open browser / scan QR → Authorize → MedMemo auto-completes.

**Implementation**: `OAuthDeviceFlowService` (`internal/adapters/auth/oauth_device_flow.go`) + `LocalCallbackServer` (`internal/adapters/auth/local_callback_server.go`)

### Tier 3: API Key Manual Input

**Mechanism**: User manually copies API Key from provider dashboard, pastes into MedMemo input field.

**User experience**: Open MedMemo → "I have an API Key" → Select provider → See step-by-step guide → Click "Go get it" (opens browser) → Copy key → Paste → Save.

**Enhancements**:
- **Smart paste detection**: Clipboard content matching `sk-...` / `AIza...` patterns auto-fills the field
- **Pre-save validation**: Backend calls `/v1/models` to verify key validity before persisting
- **"Save anyway" fallback**: If validation fails (e.g., corporate proxy), user can force save

**Implementation**: `APIKeyPanel` + `APIKeyGuide` (`web/src/components/auth/`)

### Tier 4: Local Model (Ollama)

**Mechanism**: Detect locally installed Ollama → auto-start if needed → pull SmolLM2 135M → build local ProviderConfig.

**User experience**: Open MedMemo → "Use local model (offline)" → One click → Auto-downloads model → Ready.

**Implementation**: `OllamaDetector` (`internal/adapters/ai/ollama_detector.go`)

### Unified Authentication Abstraction

All four tiers converge into a single `ProviderConfig` with `AuthMethod` and `AuthParams`:

```go
type AuthMethod string
const (
    AuthMethodAPIKey        AuthMethod = "api_key"
    AuthMethodCLIToken      AuthMethod = "cli_token"
    AuthMethodOAuthDevice   AuthMethod = "oauth_device"
    AuthMethodServiceAccount AuthMethod = "service_account"
)

type AuthParams struct {
    // API Key (all tiers)
    APIKey string

    // CLI Token (Tier 1)
    CredentialPath string

    // OAuth Device Flow (Tier 2)
    ClientID           string
    AuthURL            string
    TokenURL           string
    OAuthAccessToken   string
    OAuthRefreshToken  string
    OAuthExpiresAt     time.Time

    // Service Account (future Tier)
    GCPProjectID string
    Region       string
    SAJSON       string
}
```

**Token Resolution**: `ProviderConfig.ResolveAuthToken()` dynamically resolves the actual HTTP Bearer token based on `AuthMethod`:
- `api_key` → returns `APIKey` directly
- `cli_token` → reads credential file → returns `access_token` (or cached token if available)
- `oauth_device` → returns cached `OAuthAccessToken` (triggers refresh if expired)
- `service_account` → placeholder for future implementation

### Token Refresh & Lifecycle

```
┌─────────────────────────────────────────────────────────────┐
│  TokenRefreshService                                        │
│  • Refresh(provider) — POST grant_type=refresh_token       │
│  • ScheduleAutoRefresh(provider) — time.Timer (expire-5min) │
│  • CancelAutoRefresh(provider) — cleanup timer              │
│  • 4xx degraded — clear token, disable provider, notify UI  │
└─────────────────────────────────────────────────────────────┘
```

**Double persistence**: After refresh, new tokens are saved to both SQLite (`ProviderStore.Update`) and CLI credential files. On app restart, `ResolveAuthToken` checks the SQLite cache first — no immediate refresh required.

### Smart Detection & Recommendation

`DetectAuthMethods()` runs four goroutines in parallel (2-second timeout) to detect all tiers:

```
Parallel Detection:
  ├─ CLITokenService.Detect("kimi") / Detect("gemini")
  ├─ OAuthDeviceFlow status check
  ├─ APIKey existence (ListProviders)
  └─ OllamaDetector.Detect()

Recommendation Algorithm:
  For tier in [1, 2, 3, 4]:
    If tier.available && tier.connected:
      return tier as recommended
  Return tier 4 (local) as ultimate fallback
```

## Consequences

### Positive Impacts

- **Dramatically reduced onboarding friction**: Tier 1 users (CLI installed) can be ready in 1 click; Tier 2 users never touch an API Key string.
- **Progressive disclosure**: Users see only the tiers relevant to their environment. No overwhelming configuration screen on first launch.
- **Local-first compliance**: All tokens are stored locally (system keyring / SQLite); no central auth server, no telemetry.
- **Graceful degradation**: If all cloud tiers fail, Tier 4 (Ollama) provides a fully functional offline experience.

### Negative Impacts

- **Increased backend complexity**: Four authentication mechanisms, refresh logic, credential file parsing, and OAuth polling significantly expand the `internal/adapters/auth/` package.
- **Credential file format fragility**: CLI tool vendors may change credential file formats without notice. Mitigation: robust parsing with multiple fallback strategies (JSON struct → JSON map → plain text).
- **OAuth Device Flow client_id requirement**: Open-source apps typically lack pre-registered OAuth clients. Users must supply `client_id` for Tier 2. Mitigation: clear error messaging; Tier 1 and Tier 3 remain viable alternatives.

## Alternatives Considered

| Alternative | Rejection Reason |
|:------------|:-----------------|
| **Single API Key only** (like most ChatGPT clients) | Excludes users who have subscriptions but no API Keys; high onboarding abandonment |
| **Centralized MedMemo auth server** (proxy all requests through our backend) | Violates local-first and privacy pillars; introduces operational cost and legal liability |
| **Browser extension to scrape web session cookies** | Fragile, security-risky, violates most platforms' ToS |
| **Only CLI Token + API Key (skip OAuth)** | OAuth Device Flow is the industry standard for TV/limited-input devices; skipping it leaves a significant UX gap |
