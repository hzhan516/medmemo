# ADR-003: 采用 Provider-Factory 多模型架构

> 🌐 [English Version](../../../adr/003-multi-model-architecture.md)

- **状态**: 已采纳 (Accepted)
- **日期**: 2026-05
- **决策人**: 后端技术负责人、产品负责人

## 背景

MedMemo 的核心价值主张之一是**「多模型自由切换」**——用户必须能够根据个人偏好（隐私、成本、质量、延迟）选择自己喜欢的 AI 后端。项目面向四类差异显著的用户画像：

| 画像 | 优先级 | 偏好后端 |
|:--------|:---------|:------------------|
| 城市白领（25–35 岁） | 低延迟、高质量 | 云端大模型（Kimi / GPT-4o） |
| 家庭健康管理者（40–55 岁） | 成本控制、质量稳定 | 中端云端（通义 / 硅基流动） |
| 隐私导向的技术用户（25–45 岁） | 数据不出设备 | 本地 Ollama / llama.cpp |
| 老年子女代理（35–50 岁） | 设置简单、无需 API Key | 本地模型或预配置云端 |

硬编码单一 LLM 后端将：
1. **侵犯用户自主权** —— 迫使所有用户接受同一提供商的定价和数据政策。
2. **造成供应商锁定** —— 若唯一提供商更改定价或条款，整个产品都会受影响。
3. **阻止离线使用** —— 纯云端模型使应用在无网络时无法使用，与离线优先设计原则相悖。

应用层（`internal/application/`）必须通过统一接口与 LLM 后端交互，这样切换模型时无需修改用例编排器。

## 决策

采用 **Provider-Factory 模式**，通过统一的 `LLMClient` 接口支持 **6+ 后端提供商**，兼容 OpenAI-compatible API 协议和本地 HTTP API。

### 支持的提供商

| 类型 | 提供商 | 协议 | 默认端点 | 认证方式 |
|:-----|:---------|:---------|:-----------------|:------------|
| 云端 | Moonshot Kimi | OpenAI-compatible | `api.moonshot.cn` | API Token |
| 云端 | OpenAI GPT | OpenAI API | `api.openai.com` | API Token |
| 云端 | 阿里云通义 | OpenAI-compatible | `dashscope.aliyuncs.com` | API Token |
| 云端 | 硅基流动 | OpenAI-compatible | `api.siliconflow.cn` | API Token |
| 本地 | Ollama | HTTP REST API | `localhost:11434` | 无 |
| 本地 | llama.cpp | HTTP REST API (OpenAI-compatible) | `localhost:8080` | 无 |

### LLMClient 接口契约

接口定义在 `internal/application/port/` 中（遵循 Clean Architecture 的消费者端声明原则）：

```go
type LLMClient interface {
    Chat(ctx context.Context, messages []models.Message) (string, error)
    StreamChat(ctx context.Context, messages []models.Message, callback func(chunk string)) (*models.TokenUsage, error)
    CheckAvailability(ctx context.Context) (bool, string)
}
```

所有适配器实现完全相同的契约，确保应用层对底层提供商无感知。

### 上下文继承与窗口截断

对话中途切换模型时，上下文（消息历史）被保留。截断策略如下：

1. **锚点保留**: 始终完整保留最早的 3 轮对话 —— 它们确立了对话主题和用户意图。
2. **中间压缩**: 第 4 轮到倒数第 4 轮通过 outgoing 模型汇总为单条压缩上下文块。
3. **近期保留**: 始终完整保留最近的 3 轮对话，以保持会话连贯性。

从大型云端模型切换到较小的本地模型时，压缩率更高，且会弹出确认对话框提示用户：*「切换到本地模型可能减少上下文保留量，是否继续？」*

### 关键约束

1. **提供商配置可由用户编辑**: 用户可通过设置 UI 添加、编辑或删除提供商配置。每个配置通过 `ProviderConfig.Validate()` 进行校验（基础字段 + 认证方法参数）。
2. **端点与模型解析**: 工厂通过优先级链解析最终 API 端点和模型 ID：用户配置值 → 提供商类型默认值 → 回退常量。
3. **可用性探测**: `CheckAvailability` 执行轻量级 HEAD 或最小化补全请求；不可用的提供商在 UI 中置灰但不删除。

## 结果

### 积极影响

- **用户自主权**: 每位用户可选择匹配其隐私、成本和质量偏好的后端。
- **供应商风险缓解**: 没有单一提供商故障会导致应用不可用；用户可即时切换。
- **离线能力**: 本地 Ollama/llama.cpp 后端支持完全离线运行，满足离线优先原则。
- **社区可扩展性**: 新提供商可通过在 `internal/adapters/ai/` 中实现 `LLMClient` 接口添加，无需触碰应用逻辑。

### 消极影响

- **测试矩阵扩大**: 每个提供商适配器需要单独的集成测试（模拟服务器 + 真实 API 冒烟测试），增加了 CI 维护成本。
- **上下文切换 UX 摩擦**: 对话中途切换模型可能导致细微的行为变化（不同的分词、拒绝模式、格式）。压缩/摘要步骤增加了延迟。
- **配置复杂度**: 用户必须理解 API Key、端点和模型 ID —— 比「开箱即用」的单模型应用 onboarding 曲线更陡峭。
- **本地模型资源压力**: 在同一台机器上同时运行 Ollama、DuckDB 和 ONNX Runtime 会推高内存使用；最低推荐内存为 8GB。

## 替代方案

| 替代方案 | 拒绝原因 |
|:------------|:-----------------|
| 单一硬编码云端模型（如仅 GPT-4o） | 违反多模型切换这一核心支柱；供应商锁定；无离线能力；迫使所有用户接受同一定价模型 |
| 为所有 LLM 完全抽象的自定义协议 | 过度工程；Go 生态缺乏成熟的「通用 LLM SDK」；OpenAI-compatible API 已是事实标准 |
| 无工厂的各提供商自定义适配器 | 导致分散的初始化逻辑；违反 DRY 原则；添加新提供商更困难 |
