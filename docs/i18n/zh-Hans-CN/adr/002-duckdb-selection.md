# ADR-002: 采用 DuckDB 作为嵌入式分析型数据库

> 🌐 [English Version](../../../adr/002-duckdb-selection.md)

- **状态**: 已采纳 (Accepted)
- **日期**: 2026-05
- **决策人**: 后端技术负责人、AI 工程师

## 背景

MedMemo 是一款桌面端健康信息工具，采用**三层记忆架构**（L1 工作记忆、L2 短期记忆、L3 长期记忆）和**家族健康图谱**，需要同时支持事务型持久化和分析型查询。核心存储需求如下：

1. **事务型数据**: 对话历史、消息记录、用户设置 —— 高写入吞吐量、ACID 保证、小结果集。
2. **分析型查询**: 家族健康统计（如「三代人中出现频率最高的疾病是什么？」）、风险评分聚合、时间序列分析 —— 复杂的 GROUP BY、JOIN 和窗口函数。
3. **向量检索**: L3 长期记忆需要对嵌入向量（100 维 float32）进行语义相似度搜索，用于记忆检索增强生成（RAG）。
4. **图查询**: 家族关系网络使用属性图模型和 Cypher 查询 —— 由专门的图数据库处理。

在项目启动前，团队评估了四种嵌入式数据库方案：

| 数据库 | 优点 | 缺点 | 适用性 |
|:---------|:-----|:-----|:------------|
| **SQLite** | 成熟、经过实战检验、体积极小（~1MB）、事务性能优异 | 无原生向量索引；分析型查询（复杂 GROUP BY、窗口函数）显著慢于列式存储；fts5 仅限于关键词搜索 | ⚠️ 适合事务层，不足以支撑分析 + 向量 |
| **DuckDB** | 进程内嵌入式分析引擎；列式存储；通过 `vss` 扩展支持向量搜索；窗口函数和聚合性能出色；体积小巧（~20MB） | 相对年轻（v1.7）；写密集型事务负载并非其主要设计目标；Go 绑定通过 CGO 引入构建复杂度 | ✅ 最适合分析 + 向量层 |
| **PostgreSQL + pgvector** | 向量支持成熟；丰富的分析函数；生态强大 | 需要外部服务器进程；违反离线优先原则；部署复杂性与桌面端单二进制模型不兼容 | ❌ 违反嵌入式 / 离线优先约束 |
| **ClickHouse Local** | 极致的分析性能；通过 Annoy 索引支持向量 | 对于桌面端规模过度设计；二进制体积大（~200MB）；学习曲线陡峭 | ❌ 超出 <150MB 总部署体积预算 |

## 决策

采用 **DuckDB v1.7+** 作为 MedMemo 的嵌入式分析型数据库，与 **SQLite**（事务型存储）和 **Kùzǔ**（图数据库）协同使用。三种数据库的职责划分如下：

```
存储栈：
├── SQLite / SQLCipher     # 事务型：对话、消息、设置
├── DuckDB                 # 分析 + 向量：L3 记忆、嵌入向量、聚合统计
└── Kùzǔ                   # 图：家族关系、Cypher 查询
```

### 职责分配

| 数据类别 | 主存储 | 原因 |
|:--------------|:--------------|:-------|
| 对话与消息记录 | SQLite | 高频写入、ACID 可靠性、成熟稳定 |
| L3 长期记忆嵌入向量 | DuckDB | 通过 `vss` 扩展进行向量相似度搜索；记忆统计的分析型聚合 |
| 家族健康统计 / 风险评分 | DuckDB | 跨代数据的复杂分析查询（GROUP BY、窗口函数） |
| 家族关系图谱 | Kùzǔ | 原生属性图模型、Cypher 查询语言、高效的图遍历 |

### 关键技术选择

1. **DuckDB `vss` 扩展用于向量索引**: 在 `FLOAT[100]` 嵌入向量列上建立 HNSW（分层可导航小世界）索引，目标是在 10 万条记忆记录上实现 <30ms 的 Top-K 检索（PER-06）。

2. **DuckDB 内存模式用于单元测试**: 集成测试使用 `:memory:` DuckDB 实例，避免文件 I/O 和测试隔离问题。

3. **通过单一 Goroutine 串行化写入**: DuckDB 写操作通过单一专用 Goroutine 串行执行。读操作利用 DuckDB 的 MVCC 机制实现安全的并发访问（参见 ADR-004 运行时模型）。

4. **通过 `github.com/marcboeker/go-duckdb` 进行 Go 绑定**: 基于 CGO 的绑定，通过标准 `database/sql` 驱动暴露 DuckDB 的完整 SQL 接口。

## 结果

### 积极影响

- **分析型查询比 SQLite 快 10–50 倍**，对于聚合和窗口函数负载，直接改善了家族健康统计的响应时间。
- **原生向量搜索**: `vss` 扩展消除了对独立向量数据库（如 Milvus、Pinecone）的需求，使部署体积保持在 150MB 以内。
- **单一 SQL 方言**: DuckDB 使用标准 SQL，因此分析查询可以直接编写和测试，无需学习新的查询语言。
- **无缝 CSV/JSON/Parquet 导入**: 未来功能（如导入健康体检报告）可以利用 DuckDB 内置的格式读取器。

### 消极影响

- **CGO 构建复杂度**: 为 Windows/macOS/Linux 交叉编译需要平台特定的 DuckDB 静态库，增加了 CI 构建时间。
- **写入争用**: DuckDB 针对读密集型分析负载优化；高频事务写入（如每次按键）必须批量处理或路由到 SQLite 以避免争用。
- **生态较年轻**: DuckDB v1.7 不如 SQLite v3.45 成熟；Go 绑定或 `vss` 扩展中的边缘情况 bug 可能需要上游修复或变通方案。
- **三套数据库需要维护**: 运维、迁移和备份现在横跨 SQLite、DuckDB 和 Kùzǔ，相比单存储设计增加了运维面。

## 替代方案

| 替代方案 | 拒绝原因 |
|:------------|:-----------------|
| 全部使用 SQLite | 缺乏向量索引和分析型查询性能；复杂的家族统计查询会慢到无法接受 |
| PostgreSQL（通过 `postgres-lite` 嵌入） | 仍需要后台服务器进程；违反「单二进制、无守护进程」的桌面部署约束 |
| 单图数据库（Kùzǔ）处理一切 | Kùzǔ 擅长图遍历，但并非为高吞吐事务写入或向量相似度搜索而设计 |
