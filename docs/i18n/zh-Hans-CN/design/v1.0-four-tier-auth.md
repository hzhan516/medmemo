# ADR-002: 四层渐进式认证体系

> 🌐 [English Version](../../../design/v1.0-four-tier-auth.md)

- **状态**: 已采纳
- **日期**: 2026-05
- **决策者**: Tech Lead
- **范围**: v1.0 — 多模型自由配置系统

## 背景

MedMemo 面向多元化用户群体，包括注重隐私的技术用户、家庭健康管理者和上班族。阻碍采纳的一个重大壁垒是 API Key 的获取流程：许多潜在用户已经订阅了 LLM 服务（ChatGPT Plus、Kimi Premium），但并未持有或不知道如何获取 API Key。

v1.0 的引导流程必须在保持安全和本地优先原则的同时，最小化使用阻力。我们需要一个渐进式认证体系：
1. 自动检测已有凭证（CLI 工具缓存）
2. 为没有 API Key 的用户回退到浏览器 OAuth 授权
3. 将传统 API Key 输入作为最后手段
4. 提供完全离线的本地模型选项作为终极兜底

## 决策

实现一个**四层渐进式认证体系**，按用户便利性排序（最省力优先）：

```
Tier 1 ── CLI Token ──────────────┐
        (zero-config, auto-detect) │
Tier 2 ── OAuth Device Flow ──────┤──→ ProviderConfig.AuthMethod
        (browser auth, no key copy)│    (cli_token / oauth_device /
Tier 3 ── API Key ────────────────┤     api_key / service_account)
        (manual input, guided)     │
Tier 4 ── Local Model (Ollama) ───┘
        (fully offline, one-click)
```

### Tier 1: CLI Token 认证

**机制**: 检测并读取本地已安装 CLI 工具的缓存 access token。

- **Kimi CLI**: 解析 `~/.kimi/credentials/kimi-code.json` → 提取 `access_token`
- **Gemini CLI**: 解析 `~/.config/gcloud/application_default_credentials.json` → 提取 `refresh_token`（通过 Tier 2 机制自动刷新）

**用户体验**: 打开 MedMemo → "检测到您的 Kimi CLI 登录，是否使用？" → 一键 → 完成。

**实现**: `CLITokenService` (`internal/adapters/auth/cli_token_service.go`)

### Tier 2: OAuth 2.0 Device Authorization Grant (RFC 8628)

**机制**: 后端请求 device code → 前端展示 user code + verification URL → 用户在浏览器中授权 → 后端轮询 token 端点 → 接收 access_token。

**用户体验**: 打开 MedMemo → "使用 Kimi 登录" → 看到 8 位数字代码 + QR 码 → 打开浏览器 / 扫码 → 授权 → MedMemo 自动完成。

**实现**: `OAuthDeviceFlowService` (`internal/adapters/auth/oauth_device_flow.go`) + `LocalCallbackServer` (`internal/adapters/auth/local_callback_server.go`)

### Tier 3: API Key 手动输入

**机制**: 用户从 Provider 控制台手动复制 API Key，粘贴到 MedMemo 输入框。

**用户体验**: 打开 MedMemo → "我有 API Key" → 选择厂商 → 查看分步引导 → 点击 "去获取"（打开浏览器）→ 复制 key → 粘贴 → 保存。

**增强功能**:
- **智能粘贴检测**: 剪贴板内容匹配 `sk-...` / `AIza...` 格式时自动填充输入框
- **保存前验证**: 后端调用 `/v1/models` 验证 key 有效性后再持久化
- **"仍然保存" 兜底**: 验证失败时（如企业代理），用户可强制保存

**实现**: `APIKeyPanel` + `APIKeyGuide` (`web/src/components/auth/`)

### Tier 4: 本地模型 (Ollama)

**机制**: 检测本地已安装 Ollama → 按需自动启动 → 拉取 SmolLM2 135M → 构建本地 ProviderConfig。

**用户体验**: 打开 MedMemo → "使用本地模型（离线）" → 一键 → 自动下载模型 → 就绪。

**实现**: `OllamaDetector` (`internal/adapters/ai/ollama_detector.go`)

### 统一认证抽象

四层全部收敛到单个 `ProviderConfig`，通过 `AuthMethod` 和 `AuthParams` 区分：

```go
type AuthMethod string
const (
    AuthMethodAPIKey        AuthMethod = "api_key"
    AuthMethodCLIToken      AuthMethod = "cli_token"
    AuthMethodOAuthDevice   AuthMethod = "oauth_device"
    AuthMethodServiceAccount AuthMethod = "service_account"
)

type AuthParams struct {
    // API Key (all tiers)
    APIKey string

    // CLI Token (Tier 1)
    CredentialPath string

    // OAuth Device Flow (Tier 2)
    ClientID           string
    AuthURL            string
    TokenURL           string
    OAuthAccessToken   string
    OAuthRefreshToken  string
    OAuthExpiresAt     time.Time

    // Service Account (future Tier)
    GCPProjectID string
    Region       string
    SAJSON       string
}
```

**Token 解析**: `ProviderConfig.ResolveAuthToken()` 根据 `AuthMethod` 动态解析实际 HTTP Bearer token：
- `api_key` → 直接返回 `APIKey`
- `cli_token` → 读取凭证文件 → 返回 `access_token`（或缓存 token）
- `oauth_device` → 返回缓存的 `OAuthAccessToken`（过期时触发刷新）
- `service_account` → 未来实现占位

### Token 刷新与生命周期

```
┌─────────────────────────────────────────────────────────────┐
│  TokenRefreshService                                        │
│  • Refresh(provider) — POST grant_type=refresh_token       │
│  • ScheduleAutoRefresh(provider) — time.Timer (expire-5min) │
│  • CancelAutoRefresh(provider) — cleanup timer              │
│  • 4xx degraded — clear token, disable provider, notify UI  │
└─────────────────────────────────────────────────────────────┘
```

**双持久化**: 刷新后，新 token 同时保存到 SQLite（`ProviderStore.Update`）和 CLI 凭证文件。应用重启时，`ResolveAuthToken` 优先检查 SQLite 缓存 —— 无需立即刷新。

### 智能检测与推荐

`DetectAuthMethods()` 并行启动四个 goroutine（2 秒超时）检测全部四层：

```
Parallel Detection:
  ├─ CLITokenService.Detect("kimi") / Detect("gemini")
  ├─ OAuthDeviceFlow status check
  ├─ APIKey existence (ListProviders)
  └─ OllamaDetector.Detect()

Recommendation Algorithm:
  For tier in [1, 2, 3, 4]:
    If tier.available && tier.connected:
      return tier as recommended
  Return tier 4 (local) as ultimate fallback
```

## 后果

### 正面影响

- ** onboarding 阻力大幅降低**: Tier 1 用户（已安装 CLI）1 键就绪；Tier 2 用户无需接触 API Key 字符串。
- **渐进式披露**: 用户只看到自己环境相关的层级。首次启动不会面对 overwhelming 的配置界面。
- **本地优先合规**: 所有 token 本地存储（系统密钥环 / SQLite）；无中央认证服务器，无遥测。
- **优雅降级**: 若全部云端层级失败，Tier 4 (Ollama) 提供完全可用的离线体验。

### 负面影响

- **后端复杂度增加**: 四种认证机制、刷新逻辑、凭证文件解析和 OAuth 轮询显著扩展了 `internal/adapters/auth/` 包。
- **凭证文件格式脆弱性**: CLI 工具厂商可能不通知就更改凭证文件格式。缓解方案：健壮解析，多 fallback 策略（JSON struct → JSON map → 纯文本）。
- **OAuth Device Flow 的 client_id 需求**: 开源应用通常缺乏预注册的 OAuth 客户端。Tier 2 需要用户自行提供 `client_id`。缓解方案：清晰的错误提示；Tier 1 和 Tier 3 仍是可行替代。

## 备选方案

| 备选方案 | 否决原因 |
|:------------|:-----------------|
| **仅 API Key**（如大多数 ChatGPT 客户端） | 排除了有订阅但无 API Key 的用户；高 onboarding 流失率 |
| **中心化 MedMemo 认证服务器**（所有请求代理到我们的后端） | 违反本地优先和隐私原则；引入运营成本和法律风险 |
| **浏览器扩展抓取 web session cookie** | 脆弱、安全风险高、违反大多数平台 ToS |
| **仅 CLI Token + API Key（跳过 OAuth）** | OAuth Device Flow 是 TV/有限输入设备的事实标准；跳过会留下显著 UX 缺口 |
