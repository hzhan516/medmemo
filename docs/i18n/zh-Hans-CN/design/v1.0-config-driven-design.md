# ADR-001: 配置驱动模型接入架构

> 🌐 [English Version](../../../design/v1.0-config-driven-design.md)

- **状态**: 已采纳
- **日期**: 2026-05
- **决策者**: Tech Lead
- **范围**: v1.0 — 多模型自由配置系统

## 背景

MedMemo v1.0 的目标是在后端不硬编码任何厂商适配器的前提下，支持任意 OpenAI-compatible LLM Provider。桌面应用必须允许用户通过统一 UI 动态添加、编辑和切换 Provider（OpenAI、Kimi、DeepSeek、Claude、Ollama 等）。

在 v1.0 之前，代码库中包含厂商特定的适配器（`OpenAIAdapter`、`LocalAdapter`），硬编码了端点、认证逻辑和请求格式。新增一个 Provider 需要修改后端代码、重新编译并发布 —— 对于 Provider 生态快速演进的桌面工具而言不可接受。

## 决策

采用**配置驱动架构**：后端只维护**一个通用 HTTP 客户端**（`OpenAICompatibleClient`），所有厂商差异通过用户可编辑的运行时配置解决。

### 核心原则

```
Backend: 零厂商特定代码
Frontend: 零厂商特定逻辑（静态模板 JSON 除外）
User: 完全控制 API Host、Key、Model ID、Temperature、Timeout
```

### 架构

```
┌─────────────────────────────────────────────────────────────┐
```

### 关键设计点

1. **单一通用客户端**: `OpenAICompatibleClient` 在 `internal/adapters/ai/compat_client.go` 中接受任意 `ProviderConfig`，执行标准 OpenAI-compatible HTTP 调用。无厂商分支，无特殊处理。

2. **统一 ProviderConfig**: 单个 `pkg/models.ProviderConfig` 结构体同时服务 HTTP 客户端调用、SQLite 持久化、Wails 序列化和前端状态管理。消除 DTO 膨胀。

3. **静态模板 JSON**: 21 个预置 Provider 模板（OpenAI、Kimi、DeepSeek、Claude、Ollama 等）存储为前端静态 JSON 文件。新增模板**只需编辑 JSON** —— 无需后端发布。

4. **运行时模型切换**: 聊天界面的 `ModelSwitcher` 读取当前激活的 `ProviderConfig`，将 `modelId` 传给 `SendMessageStream`。新消息使用新选中的模型；历史消息保留不变。

5. **健康检测解耦**: `HealthEngine` 独立轮询每个 Provider 的 `/v1/models` 端点。它不依赖 `OpenAICompatibleClient` 的内部实现，直接使用标准库 `net/http`。

## 后果

### 正面影响

- **新增 Provider 零后端代码**: 支持一个新的 OpenAI-compatible 服务只需在前端 JSON 模板中增加一条记录。
- **统一错误处理**: 所有 Provider 共享相同的 `LLMError` 分类（4xx = 不可重试，5xx/429/超时 = 可重试）。
- **可测试性**: 通用客户端只需针对单个 `httptest` 服务器即可完整测试；无需模拟 20+ 厂商 API。
- **用户自主权**: 高级用户可以添加私有部署、自定义端点或实验性模型，无需等待应用更新。

### 负面影响

- **非 OpenAI-compatible Provider 不受支持**: 使用私有 API 的厂商（如某些早期国内 LLM 平台）无法直接使用。缓解方案：Ollama 的 OpenAI-compatible 模式覆盖大部分本地模型；云厂商正在快速拥抱 OpenAI API 格式。
- **功能对等性损失**: Provider 特有功能（如 OpenAI 的 function calling、Kimi 的上下文缓存）无法暴露。缓解方案：v1.0 聚焦基础 chat completion；高级功能可通过未来版本中扩展 `ProviderConfig` 的可选字段实现。
- **模板维护负担**: 21 个模板需要定期更新（模型列表、默认模型）。缓解方案：模板纯前端 JSON；CI 验证 schema 完整性。

## 备选方案

| 备选方案 | 否决原因 |
|:------------|:-----------------|
| **每个 Provider 一个厂商特定适配器**（`OpenAIAdapter`、`KimiAdapter`、`DeepSeekAdapter`...） | 维护成本高；每新增一个 Provider 都需要后端代码、测试和发布周期 |
| **插件架构（动态 .so / wasm 加载）** | v1.0 过度设计；增加了显著复杂度（插件生命周期、ABI 稳定性、安全沙箱），收益有限 |
| **代理服务器方案（中心化 MedMemo API 网关）** | 违反本地优先原则；引入网络依赖和隐私风险 |
